# 知微 · TeachCraft 性能与内存调研报告

**调研日期**：2026-10-27
**目标**：定位性能问题，评估内存压缩到 **200MB** 的可行路径
**方法**：4 个并行审查代理逐文件通读 117 个源文件（33,316 行）+ 本机实测（进程采样、GC 计数器、配置对照实验、临时文件核查）

> **重要前提**：项目在今天（1.10.1 与 1.11.0）已经落地过一轮全链路性能修复。本报告对代理提出的每一条 P0 结论都回到源码做了复核，**撤销了 4 条误报、标注了 6 条已修复项**，只保留经代码或实测确认的问题。

---

## 摘要

一句话结论：**这不是「对象泄漏」问题，而是「原生内存占大头 + 若干确定性浪费」问题。**

| 指标 | 实测值 |
| :--- | :--- |
| 空载稳态工作集（仅主窗口，1.11.0） | **264–270 MB** |
| 首轮改动后（1.11.1） | **246.8 MB（−23.3MB）** |
| 其中托管堆 | **34.4 MB**（约 13%） |
| 其中原生内存 | **约 230 MB**（约 87%） |
| LOH 碎片（LOH 20.5MB 中） | **18.9 MB（92%）** |
| 线程数 | 117–118（24 核机器） |
| 加载模块数 | 147 |
| 渲染后端 | GPU（ANGLE → D3D11） |

托管堆只有 34MB，说明**优化 C# 对象逻辑无法省出目标所需的 64MB**。要压到 200MB，主战场在三处：运行时配置、渲染与线程栈、峰值分配。

关于 200MB 的可行性，需要先拆成两个口径：

- **空载常驻 200MB**：可达，但必须组合 4 类措施，且**软件渲染是最关键的不确定项**（未验证，估 20–30MB）。
- **任何操作下都不超过 200MB**：不现实。分晓在 3000 人规模下历史实测峰值 394MB，属数据结构本身决定的下限，只能压低不能消除。

## 一、实测基线

测量对象：`src/TeachCraft.App/bin/Release/net10.0/TeachCraft.exe`（2026-10-27 13:17 构建，对应 1.11.0）与 `dist/TeachCraft-win-x64/TeachCraft.exe`（10-23 构建，对应 1.10.x）对照。测量机：24 核 / 15.4GB。

### 1.1 稳态内存

| 场景 | 工作集 | 私有字节 | 线程 |
| :--- | ---: | ---: | ---: |
| 启动 3 秒（旧构建） | 242.6 MB | 188.9 MB | 43 |
| 稳定后 · 旧构建（3 次） | 267.9 / 250.6 / 253.8 MB | 229–277 MB | 117 |
| 稳定后 · 1.11.0（3 次，18 秒） | 268.7 / 272.3 / 269.2 MB | 232.9 MB | 118 |

**新版基线均值约 270MB**。1.11.0 比 1.10.x 略高（+6MB），与新增「教师分工」五视角的数据结构相符，不构成回归。

空闲 10 秒内工作集不回落（最低值等于稳态值），说明**没有任何主动归还机制**——停在哪就是哪。

### 1.2 托管堆分解（决定性数据）

用 `dotnet-counters` 采集 `System.Runtime` 8 秒：

| 堆区 | 大小 |
| :--- | ---: |
| Gen0 | 4.39 MB |
| Gen1 | 9.41 MB |
| Gen2 | 0.00 MB |
| **LOH（大对象堆）** | **20.51 MB** |
| POH | 0.05 MB |
| **合计** | **34.4 MB** |

两个关键发现：

1. **LOH 碎片 18.92MB，占 LOH 的 92%**。LOH 里真正存活的大对象只有约 1.6MB，其余全是释放后留下的碎片。成因是「生成大字符串/大数组 → 释放」的循环（自动保存的整份 JSON、导出缓冲）。
2. **空载 8 秒仅分配 0.6MB**。没有后台泄漏循环，空闲时干净。所有问题都出在「执行某个操作时」。

### 1.3 GC 配置对照实验（结论不稳定，需复验）

每组 14–18 秒稳态，新旧构建分别测：

| 配置 | 旧构建（2 次均值） | 1.11.0（3 次） |
| :--- | ---: | ---: |
| 基线 | 263.8 MB | **270.1 MB** |
| `GCConserveMemory=5` | 262.8 MB（无效） | — |
| `GCConserveMemory=9` | 243.3 MB（**−20.5**） | 265.3 MB（**−4.8，方差 254–272**） |
| `gcServer=1` | 264.9 MB，线程 141 | — |
| `TieredPGO=0` | 244.2 MB | — |

**必须如实说明**：同一个配置在旧构建上稳定复现 −20MB，在新构建上只有 −5MB 且方差极大。可能原因是 GC 归还时机受当时机器负载影响（测量期间有并行代理进程）。因此：

- `GCConserveMemory=9` **可以加**（零风险、无副作用），但它**不是可靠的主力手段**，不要按 −20MB 做容量规划。
- `gcServer=1` 明确负收益（+1MB，线程 +24），不要开。
- `TieredPGO=0` 能省 20MB 但牺牲热路径优化，属于拿性能换数字，不推荐。

### 1.4 发布配置：零调优

`TeachCraft.runtimeconfig.json` 的 `configProperties` 只有 3 条 MVVM/序列化默认值，**没有任何 GC / 线程 / 分层编译配置**。仓库中没有 `runtimeconfig.template.json`；MSBuild 里没有 `ServerGarbageCollection`、`ConcurrentGarbageCollection`、`InvariantGlobalization`、`PublishReadyToRun`、`PublishTrimmed` 中的任何一项；工作流只有 `PublishSingleFile=true`。

### 1.5 渲染后端与线程

进程加载了 `av_libGLESv2.dll`、`d3d11.dll`、`dxgi.dll`、`Avalonia.Vulkan.dll`——确认走 **GPU 渲染（ANGLE 转 D3D11）**。GPU 路径要维护 D3D11 设备、交换链纹理、编译后的 shader、GL 状态机，在 1200×840 的窗口上通常值 **20–40MB**。

117 个线程：本机 24 核，.NET 线程池最小线程数默认等于核数，Skia/渲染的并行度也跟随核数。一个单窗口教师工具，正在用服务器规格的线程配置运行。

## 二、核心判断：为什么不能只优化 C#

264–270MB 里托管堆占 34MB。即使把托管堆优化到 0，也只到 230MB。所以：

- **减少对象分配的改动，只能改善峰值和 GC 停顿，压不动空载常驻。**
- 空载的 230MB 原生内存，来自 .NET 运行时自身、Avalonia/Skia 渲染栈、字体、线程栈、GC 预占区。**只能靠配置和架构改。**

## 六、分模块说明

### 6.1 工具箱（TeachCraft.App / Core）

- `ImageToolbox.Encode` 已有正确做法：注释明确说明不走 `SKData` 以免整张编码结果再缓冲一份，保持。
- `PdfToolbox.cs:414-416` 的 `memory.ToArray()` 是本节唯一确定的浪费点。
- 图片链路（`SKCodec` + `Resize`）此前已优化，属健康区。

### 6.2 织序（GradeWeave）

- 自动保存是**唯一确定存在的常驻浪费**：`Serialize` 在 UI 线程把整份工程变成 JSON 字符串（30 班约 1MB），再交给后台落盘。这同时解释了 LOH 碎片和保存瞬间的 UI 卡顿。
- 排课与冲突分析已在 `Task.Run` 中执行，写法正确，无算法级问题。

### 6.3 归位 / 时序（SeatGrid / ClassBlock）

- 归位有「渲染好但没删」的临时文件，实测 `%TEMP%\TeachCraft\SeatGrid\` 残留 3 个 138KB 文件（10-23 至今）。
- 归位预览 `new Bitmap(path)` 全尺寸解码，是最容易吃出百 MB 单次峰值的地方。
- 时序预览 2.0 倍渲染 → 4 倍内存浪费，是这个模块最划算的改动（约 21MB → 5MB）。
- 窗口生命周期干净：四个子窗口单实例复用，`Closed` 时字段置 `null`，无「开一次涨一次」。

### 6.4 分晓（GradeStrip）

历史实测记录（`.memory/06`，3000 人 × 10 科）：

- 导入 0.9s；报表 3000×30 加载 271ms；导出 5.12s / **947MB 分配** / **峰值工作集 156MB**。
- **3000 人成绩条页应用后峰值约 394MB**。

这两组数字说明：分晓的峰值由「3000 行 × 数十万控件」决定，虚拟化和 `RangeObservableCollection.ReplaceAll` 已经做过了，进一步压缩只能从「同时保留几份数据」入手（切页签释放集合的策略已实现）。**不建议把 200MB 目标套到分晓的 3000 人场景上**——这是数据结构下限，不是缺陷。

### 6.5 全局配置

除了 1.4 节说的「零调优」，还有两点值得记录：

- `Avalonia.Fonts.Inter` 被 `GradeStrip.App` 引用（1.89MB 程序集内含字体族）。若分晓界面未实际使用 Inter，应移除引用，避免字体族被注册。
- 147 个加载模块中，`Avalonia.X11`、`Avalonia.Native`、`Avalonia.Vulkan` 属于异平台/备用后端，仅映射不提交，影响很小，不值得处理。

## 七、到 200MB 的路径

首轮低风险改动已落地，当前 **246.8MB**（见第十一节），距目标还需 **−47MB**。

| 档位 | 措施 | 预期收益 | 状态 |
| :--- | :--- | ---: | :--- |
| **A 配置** | `GC.ConserveMemory=9` | **−23.3MB（已实测）** | ✅ 已完成 |
| **B 渲染** | 软件渲染 A/B | −20~30MB（未验证） | 待决策 |
| **C 线程** | `ThreadPool.SetMinThreads(8,8)` | −8~15MB | 待做 |
| **D 位图** | 预览按显示尺寸解码 | **−15MB 常驻（已完成）** | ✅ 已完成 |
| **E 字体资源** | 移除未使用的 Inter 引用 | −2~4MB | 待做 |

**剩余可控空间：C + E 约 −10~19MB → 228~237MB。** 也就是说，不做渲染改造的话，能稳定落在 230MB 附近，**到不了 200MB**。

**能否跨过 200MB，仍然取决于软件渲染**。如果它真能省 25MB 以上，叠加 C+E 后落在 203~212MB，还需要再想办法挤最后几 MB；如果软件渲染被证伪（省不到 15MB），那么 200MB 这个目标就需要**动架构**：把四个子应用改为真正独立的按需加载，或者接受「空载 230MB、使用峰值 300MB」的现状。

**建议先做一次软件渲染 A/B 实测，再决定目标是否调整。** 这是唯一能改变结论的变量。

## 九、待验证清单

1. **软件渲染的真实收益**（决定 200MB 可行性）：`Program.cs` 加 `Win32PlatformOptions { RenderingMode = [Software] }`，同机 A/B，记录空载工作集 + 面板动画帧率。**收益 <15MB 就不值得做。**

## 十一、首轮低风险改动（已落地，版本 1.11.1）

按「只做零风险项、渲染留给后续决策」的约定，本轮落地 4 处：

| 改动 | 文件 | 说明 |
| :--- | :--- | :--- |
| 归位预览按 1600 宽解码 + 后台线程 | `SeatGrid.App/SeatPreviewWindow.axaml.cs` | 原 `new Bitmap(path)` 在 UI 线程解原图；最大布局 8000×2624 要 84MB，现在约 8MB，窗口先出图后补 |
| 归位预览临时图关窗即删 + 一天前兜底清理 | 同上 + `SeatChartRenderer.RenderPngToTemp` | 只删 `%TEMP%\TeachCraft` 下的本程序产物，不碰用户文件；异常退出的残留由下次渲染时清理 |
| 时序预览 2.0 倍 → 1.25 倍 | `ClassBlock.App/ClassBlockViewModel.cs` | 显示区约 1040 逻辑像素，2 倍是 4 倍像素浪费；导出/打印倍率不变 |
| GC 内存压缩 | 新增 `src/TeachCraft.App/runtimeconfig.template.json` | `System.GC.ConserveMemory = 9`，随程序集发布生效，无需环境变量 |

### 实测效果

| 指标 | 改动前 | 改动后 |
| :--- | ---: | ---: |
| 空载工作集 · 启动 8 秒 | — | 268.9 MB |
| 空载工作集 · 稳态 18 秒（3 次） | 268.7 / 272.3 / 269.2（均值 **270.1**） | 258.6 / 240.9 / 241.0（均值 **246.8**） |
| 变化 | — | **−23.3 MB（−8.6%）** |

需要注意：`ConserveMemory` 是**收缩型**策略，它的收益要等一次完整 GC 才兑现。启动后 8 秒内仍是 269MB，18 秒后才落到 241–259MB。如果希望「打开就低」，需要在启动完成后（主窗口首次空闲）主动触发一次 `GC.Collect(2, GCCollectionMode.Optimized, blocking: false, compacting: true)`——这是常见做法，但属于手动 GC 反模式，本轮没有引入，留给后续评估。

比第二轮用环境变量测得的 −4.8MB 明显更好，说明 **GC 配置必须写进 `runtimeconfig.template.json` 才稳定生效**，`Start-Process` 时临时设环境变量会受父进程环境影响。

### 回归验证
